BACKEND FIXES 1 — PRODUCTION HARDENING

IMPORTANT: Do NOT rebuild the backend from scratch unless absolutely necessary. Inspect the current backend implementation and modify the existing system.

The goal of this fix is to make the ticketing backend reliable for a large event, with clear role permissions, reliable email delivery, permanent ticket/QR association, complete statistics, and support for approximately 15,000 attendees/ticket records.

Do not break the existing ticket submission, approval, QR, check-in, revenue, or authentication functionality.

1. SUBMISSION ORDERING

The reviewer/admin submission list must display applications in the order they were received.

Default ordering

Newest submission first:

Latest submission
↓
Older submission
↓
Older submission

Every submission must have a reliable server-generated timestamp such as:

createdAt

Do NOT rely on the user's browser clock.

Use the backend/database timestamp.

Sorting/filtering

The reviewer and admin interfaces must be able to:

Sort newest → oldest
Sort oldest → newest
Filter by date/time range
Filter by status
Filter by ticket type
Search by relevant ticket information

Example:

All
Pending
Approved
Rejected
Checked In
University
Outsider

Date/time filtering should work using the stored server timestamp.

2. EMAIL DELIVERY — FIX COMPLETELY

The current email delivery is not working reliably.

Implement the necessary production email service and make sure it actually works.

Do NOT leave a fake:

Email sent successfully

response when no email was actually delivered/accepted by the configured email service.

Email architecture

Use a reliable transactional email provider/service appropriate for production.

Keep credentials in environment variables.

Never hard-code:

SMTP passwords
API keys
Email credentials
Secret tokens

Provide a .env.example showing required configuration.

3. EMAIL PROCESS

When a reviewer approves an application:

APPROVAL
   ↓
Create/retrieve ticket
   ↓
Generate/retrieve QR
   ↓
Persist ticket + QR
   ↓
Queue email
   ↓
Email service sends ticket

The email should contain the correct ticket belonging to that specific person.

Include:

Attendee name
Ticket type
Ticket/reference number
Event name
QR code
Relevant event information
Check-in instructions
4. EMAIL MUST NOT CREATE DUPLICATE TICKETS

Email delivery and ticket creation must be separate operations.

If email fails:

DO NOT:

Create another ticket
Create another QR
Approve the application again
Charge/record another ticket
Change the attendee's identity

Instead:

Ticket remains valid
Email status = FAILED
Admin can retry email

When retrying:

Existing ticket
+
Existing QR
+
Same attendee

must be reused.

5. EMAIL DELIVERY STATUS

Store email status.

Example:

PENDING
SENT
FAILED

Store useful operational information such as:

Attempt count
Last attempt time
Last failure reason
Sent timestamp

Do not expose sensitive provider credentials or internal errors to users.

Admin should be able to identify tickets where email delivery failed.

6. EMAIL RETRY

Provide a controlled retry mechanism for authorized admin users.

When retrying:

DO NOT generate a new ticket.
DO NOT generate a new QR.
DO NOT create another application.
DO NOT alter the ticket owner.

Only resend the existing ticket.

Use retry/backoff logic for temporary provider/network failures where appropriate.

Do not continuously retry permanent failures.

7. QR ↔ PERSON ASSOCIATION

This is critical.

Every generated QR must be permanently associated with the exact approved ticket/person who owns it.

The relationship must be stored in the database.

Conceptually:

Attendee
   ↓
Application
   ↓
Ticket
   ↓
QR Credential

The system must always be able to retrieve:

QR → Ticket → Attendee

and:

Attendee → Ticket → QR
8. QR RETRIEVAL FOR REVIEWER/ADMIN

A reviewer/admin must always be able to retrieve the generated QR for an approved ticket.

If the email was lost or failed, the QR must still be available from the system.

From the ticket/application record, authorized staff should be able to see:

Attendee name
Ticket ID
Ticket type
Registration number if applicable
QR status
QR image / QR representation
Email delivery status
Approval information
Check-in status

The QR should not depend on the email existing.

9. QR REGENERATION RULE

Do not casually generate a new QR every time the ticket page is opened.

A ticket should have one active QR credential.

If an image needs to be regenerated for display/email:

Reuse the same QR token.

Do not create another credential.

Only an explicitly authorized administrative recovery/revocation process may replace a QR credential.

If a QR is replaced, invalidate the old credential and create a clear audit record.

10. QR SECURITY

Do not put unnecessary personal information inside the QR.

Use a secure, unpredictable token/reference.

The QR should resolve to a backend-verifiable ticket credential.

The database remains the source of truth.

Do not trust information encoded only in the QR.

11. TICKET STATISTICS — NO ARTIFICIAL LIMIT

There must be NO hard-coded ticket quantity limit.

Do not implement something such as:

if soldTickets >= 1000:
    reject

unless a future configurable event capacity is explicitly added.

For the current system, tickets should not be artificially capped.

13. REVENUE CALCULATION

Use the authoritative backend ticket price.

Current prices:

University = Rs. 200
Outsider = Rs. 1000

Examples:

100 university tickets = Rs. 20,000

100 outsider tickets = Rs. 100,000

Total revenue:

University revenue + Outsider revenue

Store monetary values safely using integer currency units or an appropriate exact monetary representation.

Never trust a price sent by the frontend.

14. STATISTICS MUST REMAIN CONSISTENT

Avoid calculating different numbers in different parts of the admin dashboard.

Create a centralized backend statistics service/query.

For example:

GET /api/admin/statistics

should provide a consistent snapshot.

The dashboard should not make unnecessary repeated requests for every individual statistic.

15. SUPPORT APPROXIMATELY 15,000 CROWD

The system should be designed to comfortably handle an event population of approximately:

15,000 people

This does NOT mean there should be a ticket limit of 15,000.

It means the architecture should be capable of handling the expected event scale.

Design for:

15,000+ ticket records
Large submission volume
Large application history
Large check-in activity
Concurrent QR scans
Concurrent API requests
Administrative monitoring

17. ADMIN LIST PERFORMANCE

For thousands of submissions, NEVER return all records in one API request.

Example:

GET /api/admin/applications?page=1&limit=50

The exact implementation can vary according to the existing backend.

Use reasonable maximum page sizes.

Prevent users from requesting enormous datasets in one request.

18. 15,000-PERSON CHECK-IN

The check-in system must be optimized for event-day usage.

QR verification should use an indexed lookup.

Do not retrieve the entire attendee database for every scan.

Expected flow:

QR scan
 ↓
Extract secure token
 ↓
Indexed ticket lookup
 ↓
Validate status
 ↓
Atomic check-in
 ↓
Return result

The response should be fast enough for continuous event-day scanning.

19. CONCURRENT QR SCANS

This must remain concurrency-safe.

If the same QR is scanned simultaneously by two staff members:

Scan A → SUCCESS
Scan B → ALREADY CHECKED IN

Never:

Scan A → SUCCESS
Scan B → SUCCESS

Use an atomic transaction/database operation.

The ticket must become invalid for future entry immediately after the successful check-in.

21. ADMIN PORTAL ACCESS

ONLY ADMIN ROLE may access the Admin Portal.

Approvers must NOT have access to the Admin Portal.

Check-in staff must NOT have access to the Admin Portal.

Normal users must NOT have access to the Admin Portal.

This restriction must be enforced by the backend, not just by hiding frontend navigation.

If a non-admin manually enters the admin URL/API:

403 FORBIDDEN

or equivalent secure response.

23. ADMIN DELETE FUNCTION

Only the Admin may delete a submission.

This must be treated as a high-risk destructive operation.

Before deletion:

Display a clear warning such as:

Warning: This is a permanent administrative action. Deleting this submission may affect the associated application, ticket, QR record, revenue statistics, and audit history. Confirm only if you are certain this record should be removed.

Require explicit confirmation.

Do NOT allow accidental deletion through a single click.

24. DELETE AUDITING

Even when an admin deletes a submission, preserve an audit record where legally/operationally appropriate.

Record:

Admin identity
Deleted record/reference
Reason if required
Timestamp
Action performed

Do not silently erase evidence of the administrative action.

If the data model requires retaining financial/audit records, use soft deletion/archival rather than physically destroying those records.

Important: Do not allow deletion to corrupt revenue statistics or audit history.

For example:

APPROVER

Never allow a normal user to elevate their own privileges.

Privilege changes must be performed through authorized admin-only backend endpoints.

Every privilege change must generate an audit record.

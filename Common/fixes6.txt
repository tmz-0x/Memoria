# PART 1 — CINEMATIC INTRO SPOTLIGHTS

## 1. TWO MAIN SPOTLIGHTS MUST BE ON OPPOSITE SIDES

The cinematic intro must contain **two primary theatrical spotlights**.

### LEFT MAIN SPOTLIGHT

The first spotlight is permanently positioned on the:

**LEFT SIDE of the cinematic intro**

### RIGHT MAIN SPOTLIGHT

The second spotlight is permanently positioned on the:

**RIGHT SIDE of the cinematic intro**

They should face toward the central stage area.

Conceptually:

```text
     LEFT LIGHT                         RIGHT LIGHT
         \                                  /
          \                                /
           \                              /
            \                            /
             \                          /
              \                        /
               \                      /
                  CENTRAL STAGE
```

The two lights should frame the central cinematic stage.

---

# 2. SPOTLIGHT POSITION MUST NEVER MOVE

This is the most important correction.

The physical position of both main spotlights must remain completely fixed.

The following must NEVER change:

* X position
* Y position
* screen position
* beam origin
* distance from the edge
* vertical placement

The mouse must NOT translate the spotlights.

Do NOT use:

* `translateX`
* `translateY`
* mouse X → position
* mouse Y → position
* orbiting
* panning
* moving the light source

The light sources stay at their original fixed positions.

---

# 3. ONLY ROTATION/ANGLE RESPONDS TO MOUSE

The **rotation/aiming angle of the light beam** should respond to mouse movement.

This is different from moving the spotlight.

Think of a physical theatre spotlight mounted at a fixed point:

```text
FIXED LIGHT ●
             \
              \
               \
                STAGE
```

When the visitor moves the mouse, the spotlight remains at:

```text
FIXED LIGHT ●
```

but the **beam direction/angle rotates** from that fixed point:

```text
       Mouse left:

       ● \
          \
           \
            STAGE


       Mouse center:

       ●
        \
         \
          STAGE


       Mouse right:

       ●
        \
         \
          STAGE
```

The light source itself does NOT move.

Only its beam/rotation changes.

---

# 4. ROTATION RESPONSE MUST BE CLEARLY VISIBLE

The previous implementation was too subtle.

Make the mouse-controlled rotation noticeably visible.

When the mouse moves from left to right:

* left spotlight beam should visibly adjust its angle
* right spotlight beam should visibly adjust its angle
* both remain anchored to their fixed positions
* rotation should be smooth
* movement should have cinematic easing

The user should clearly notice:

**"The spotlights are following my mouse with their light direction."**

But they should NOT feel like the entire light source is moving.

---

# 5. ROTATION LIMITS

Keep the rotation controlled.

Do not allow the spotlights to rotate wildly.

Use a limited theatrical range.

For example:

* approximately ±8° to ±15° depending on screen size

Adjust according to the existing visual composition.

The two lights should remain aimed toward the stage.

They should never rotate so far that they point completely away from the central stage.

---

Make the two primary spotlight beams considerably more visible.

Increase:

* beam opacity

* bloom

The beams should clearly stand out against:

**deep violet / indigo darkness.**

# 7. ROTATION + BRIGHTNESS

# 22. ONE STUDENT TICKET PER REGISTRATION NUMBER

This is a strict business rule.

A university registration number can receive:

**ONLY ONE UNIVERSITY STUDENT TICKET.**

For example:

```text
FC122716 → Student Ticket #1
```

A second attempt:

```text
FC122716 → Student Ticket #2
```

MUST be rejected.

Display a clear message:

> A university student ticket has already been issued for this registration number.

---

# 23. DUPLICATE VALIDATION MUST BE SERVER-SIDE

Do NOT rely only on the frontend.

The backend/API must check whether the registration number already exists.

Correct flow:

```text
Select Student Ticket
        ↓
Enter Registration Number
        ↓
Frontend format validation
        ↓
Submit request
        ↓
Backend validation
        ↓
Check existing student tickets
        ↓
Already exists?
     /        \
   YES         NO
    ↓           ↓
 Reject      Create Ticket
```

This must protect against:

* duplicate submissions
* page refreshes
* multiple tabs
* manually crafted API requests
* race conditions

---

# 24. DATABASE UNIQUENESS

Where a persistent database/data layer exists, enforce a uniqueness constraint on the university registration number for student tickets.

Conceptually:

```text
student_registration_number
        UNIQUE
```

This is an additional protection beyond frontend validation.

Use an atomic operation/transaction where applicable so two simultaneous requests cannot both create tickets for the same registration number.

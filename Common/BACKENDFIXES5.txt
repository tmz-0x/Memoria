FIXES 5 — FINAL PRODUCTION HARDENING, SECURITY, QR REGENERATION, DELETION, CAMERA ACCESS & ADMIN FINALIZATION

You are working on an existing event ticket management and attendance system.

This is the FINAL major development and hardening phase.

Do NOT rebuild the application.

Do NOT remove existing working functionality.

Do NOT introduce unnecessary new features.

Do NOT change the existing visual design/theme unless required for the fixes below.

The goal is to make the existing application reliable, secure, production-ready, and clean.

Before changing anything, inspect the existing architecture, database, authentication, authorization, ticket lifecycle, QR generation, email system, check-in system, admin system, and existing testing/debugging features.

Reuse the existing architecture wherever possible.

1. QR CODE REGENERATION + REGENERATION EMAIL

The existing system allows an administrator to regenerate a ticket QR code.

This functionality must be completed properly.

When an administrator regenerates a QR code:

Generate a new secure QR/token.
Invalidate the previous QR/token.
Store the new QR/token in the database.
Ensure the old QR code can no longer be used for attendance/check-in.
Update the ticket record.
Generate the new QR image.
Send the newly generated QR code to the ticket holder's registered email.
The email must clearly indicate that this is a regenerated/reissued QR code.
The previous QR must not remain valid.
Record the operation in the audit log.

The email should clearly communicate something similar to:

"Your event QR code has been regenerated by the event administration. Please use this new QR code for entry. Any previously issued QR code is no longer valid."

Use the existing email/SMTP infrastructure.

Do not create a separate email system.

2. QR REGENERATION EMAIL TEMPLATE

Create/use a dedicated email template for QR regeneration.

The email should contain:

Attendee name
Event name
Ticket/reference number
Updated QR code
Important entry instructions
Notice that the previous QR code is invalid
Event date/time where available
Support/contact information where already configured

Do not expose internal database IDs or security tokens unnecessarily.

The QR should be attached or embedded using the existing ticket-email mechanism.

3. QR REGENERATION SECURITY

QR regeneration must be performed transactionally.

Correct sequence:

Database transaction:
invalidate old QR
create new QR/token
update ticket
commit

Then send the email.

If email sending fails after the QR was successfully regenerated:

Do NOT roll back the QR merely because email failed unless the existing architecture specifically requires transactional email.
Record the email failure.
Show the administrator that QR regeneration succeeded but email delivery failed.
Provide an appropriate "Resend regenerated QR" option.

Never leave the system in a state where both the old and new QR codes are valid.

4. QR TOKEN SECURITY

Review the QR implementation.

Do not use predictable QR values such as:

12345
TICKET001
database ID
incrementing numbers

Use secure random tokens/identifiers.

The QR should identify the ticket securely without exposing unnecessary personal information.

The backend must perform the actual validation.

Do not trust information encoded directly inside the QR without server-side verification.

5. DELETE TICKET/USER — REAL DATABASE DELETION

Fix the existing delete functionality.

If an administrator deletes an individual ticket/user/submission where the system's business rules allow permanent deletion:

The deletion must actually remove the corresponding record from the database.

Do NOT merely:

Hide it from the frontend.
Mark it as deleted without the requested behavior.
Remove it from React state.
Remove it from localStorage.
Remove it from a table while leaving the database record untouched.

After deletion:

Database state must reflect the deletion.

6. DELETE ONE RECORD WITHOUT RESETTING EVERYTHING

Deleting one record must affect ONLY that intended record.

Do NOT:

Reset all tickets.
Reset all users.
Reset counters incorrectly.
Delete unrelated attendance records.
Delete unrelated approvals.
Reset the entire database.
Reinitialize the ticket pool.

The operation must be targeted.

Example:

Admin deletes:

Ticket #A123

Only the data associated with #A123 should be affected according to the application's data relationships.

7. DELETED USER MUST BE ABLE TO GET A NEW TICKET

This is an important business rule.

If a user's ticket/submission is deleted, the system must allow that person to submit/request/purchase a ticket again according to the normal ticket workflow.

The deleted record must not permanently block the person's email/registration number/identifier unless there is an explicit business rule requiring that restriction.

Review:

Unique database constraints
Email uniqueness
Registration number uniqueness
Ticket ownership
Submission records
Approval records
Payment records
Soft-delete logic
Foreign keys

If the existing database uses a unique constraint that prevents a deleted user from registering again, fix the lifecycle correctly.

Do NOT simply remove database uniqueness constraints blindly.

The correct behavior should be:

Previous record deleted
↓
New registration/request
↓
New ticket record
↓
Normal approval/ticket workflow

8. HANDLE RELATED RECORDS CORRECTLY

Before deleting a ticket/user/submission, inspect related records:

Use appropriate:

IMPORTANT:

Audit logs should generally NOT be deleted simply because the associated user/ticket was deleted.

The audit trail should remain useful for accountability.

For example:

should remain in the audit system.

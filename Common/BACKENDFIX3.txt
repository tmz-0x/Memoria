Backend sends the email through the configured SMTP service.

Store email delivery status.

PENDING
SENT
FAILED

Store:

emailStatus
emailSentAt

4. IMPORTANT — COUNT TICKETS CORRECTLY

Do not simply count applications and call that "tickets sold."

These are different concepts.

For example:

Applications submitted
≠
Applications approved
≠
Tickets issued
≠
Tickets checked in

The statistics service must distinguish them.

Applications

Count submitted application records.

Approved

Count applications whose status is:

APPROVED

according to the existing workflow.

Rejected

Count applications whose status is:

REJECTED
Tickets sold/issued

Count actual valid ticket records according to the project's ticket state/business rules.

Do NOT count rejected applications as sold tickets.

Do NOT count pending applications as sold tickets.

Do NOT create duplicate counts if one application has multiple related records.

5. REVENUE MUST BE CENTRALIZED

Revenue must NEVER be calculated independently by frontend pages.

The backend must calculate it from authoritative ticket/payment data.

For each valid ticket, use the backend-authoritative price:

University Student = Rs. 200
Outsider = Rs. 1000

Do not trust a price supplied by the frontend.

For example:

University tickets × Rs. 200
+
Outsider tickets × Rs. 1000
=
Total revenue

However, preferably calculate revenue from the persisted authoritative ticket/payment amount rather than hard-coding calculations in multiple locations.

Use integer rupee amounts.

Example:

200
1000

not floating-point monetary values.

15. QR REGENERATION

Keep the SAME ticket ID.
Do not create another ticket.

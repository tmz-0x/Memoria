BACKEND IMPLEMENTATION — MEMORIA'26 TICKETING SYSTEM
CORE INSTRUCTION

Build the backend for the existing Memoria'26 — The Eclipse of Memories ticketing website.

DO NOT rebuild the frontend.

The backend must be production-oriented, reliable, optimized, secure, and designed to handle concurrent submissions and QR scans without duplicate tickets, inconsistent states, race conditions, or unnecessary delays.

Before implementing anything:

Inspect the existing project structure.
Inspect the current frontend ticket forms and API calls.
Inspect the existing backend/API/mock API implementation.
Reuse compatible existing architecture where practical.
Replace mock behavior only where a real backend implementation is required.
Do not break existing frontend routes or functionality.

Choose the most efficient stable backend stack appropriate for the existing React/Vite application. Prefer a lightweight TypeScript backend if it integrates cleanly with the current project.

The implementation must be modular and maintainable.

1. SYSTEM ARCHITECTURE

The backend must have clear separation between:

API/routes
Controllers/handlers
Business logic/services
Database/repository layer
Validation
Authentication/authorization
QR generation
Email service
Payment/revenue logic
Audit/activity logging
Error handling
Configuration/environment variables

Do not put all business logic inside route handlers.

Use asynchronous operations correctly.

Do not block the event loop with unnecessary CPU-heavy operations.

2. TICKET TYPES

There are exactly two public ticket categories:

UNIVERSITY STUDENT

Price:

Rs. 200

Required:

Full name
Email
University registration number
Other required ticket/form information

Registration number format example:

FC122716

The actual validation should follow the configured university registration-number pattern rather than blindly accepting arbitrary text.

OUTSIDER

Price:

Rs. 1000

Required:

Full name
Email
Other required ticket/form information

Registration number:

NOT required

3. PRICE MUST NEVER BE TRUSTED FROM THE FRONTEND

The frontend must NOT be allowed to decide the final ticket price.

For example, never trust:

price = 200

sent from the browser.

Instead:

ticketType = UNIVERSITY

or

ticketType = OUTSIDER

is submitted.

The backend determines the price:

UNIVERSITY → Rs. 200
OUTSIDER → Rs. 1000

This prevents users from manipulating prices through browser developer tools.

4. FORM VALIDATION

Validate every input on the backend.

Frontend validation is useful for UX but is NOT a security boundary.

Validate:

Full name
Email
Ticket type
University registration number when applicable
Uploaded payment slip/reference information if applicable
Required fields
String lengths
Allowed characters
Data formats
File type/size where uploads are supported

Reject invalid requests with structured error responses.

Do not allow:

Empty required values
Invalid email addresses
Unsupported ticket types
Malformed registration numbers
Unexpected fields where strict validation is appropriate
Extremely long input values
Invalid file types
Oversized uploads

Normalize relevant values before validation/storage.

For registration numbers, normalize case and unnecessary whitespace so:

FC122716
fc122716
 FC122716

cannot bypass uniqueness validation.

5. UNIVERSITY REGISTRATION NUMBER UNIQUENESS

This is a critical business rule.

A university registration number can receive ONLY ONE TICKET.

Example:

FC122716 → Ticket A

A second application using:

FC122716

must be rejected.

This rule MUST be enforced at the database level, not only with frontend validation or a preliminary API check.

Use a unique constraint/index on the normalized registration number for university tickets.

Do not rely only on:

SELECT → check exists → INSERT

because two simultaneous requests can bypass this through a race condition.

The database must guarantee uniqueness.

6. OUTSIDER TICKETS

Outsiders do not require a university registration number.

Therefore:

ticketType = OUTSIDER
registrationNumber = null

must be valid.

Do not apply the university registration-number uniqueness rule to outsider tickets.

7. APPLICATION / TICKET LIFECYCLE

Create an explicit ticket/application state machine.

Suggested states:

PENDING_REVIEW
APPROVED
REJECTED
QR_ISSUED
CHECKED_IN

If payment/slip verification requires an intermediate state, add an appropriate state such as:

PAYMENT_PENDING

Do not allow arbitrary status changes.

Define valid transitions.

For example:

PENDING_REVIEW
      ↓
APPROVED
      ↓
QR_ISSUED
      ↓
CHECKED_IN

Rejection:

PENDING_REVIEW
      ↓
REJECTED

Invalid transitions must be rejected.

8. SUBMISSION FLOW

When a user submits the ticket form:

Step 1

Frontend sends the application to the backend.

Step 2

Backend validates the request.

Step 3

Backend determines the correct ticket price based on ticket type.

Step 4

Backend validates university registration number when ticket type is UNIVERSITY.

Step 5

Backend checks/enforces registration-number uniqueness.

Step 6

Store the application.

Initial status:

PENDING_REVIEW
Step 7

Create an audit/activity record.

Step 8

Make the application available to the authorized reviewer/admin.

The QR code must NOT be generated yet.

9. MANUAL APPROVAL IS THE ONLY APPROVAL STEP

This is extremely important.

The system must NOT automatically approve applications.

The reviewer/admin must manually inspect:

Submitted details
Ticket type
Registration number where applicable
Payment slip/payment evidence
Other required information

Only an authorized reviewer can approve or reject.

No frontend request should be able to directly set:

status = APPROVED

without authorization.

10. APPROVAL FLOW

When the reviewer clicks Approve:

Backend must:

Verify reviewer authorization.
Verify the application is currently in a valid state.
Re-check all critical business rules.
Confirm the application has not already been approved.
Confirm the registration number has not been used.
Determine the backend-controlled ticket price.
Generate a unique ticket identifier.
Generate a cryptographically secure QR token.
Store the QR/ticket information atomically.
Change status appropriately.
Create an audit record.
Trigger the ticket email.

Do not generate duplicate QR codes if the reviewer accidentally clicks Approve twice.

Approval must be idempotent.

11. QR CODE GENERATION

After successful approval, generate a unique QR code.

The QR should contain a secure opaque ticket identifier/token, not unnecessary personal information.

Do NOT encode sensitive personal data directly into the QR.

Example conceptual payload:

MEMORIA26:TICKET:<secure-random-token>

Use a cryptographically secure random value.

The token must be:

Unique
Unpredictable
Sufficiently long
Stored securely
Associated with exactly one ticket

Do not use:

1
2
3

or predictable ticket IDs as the security token.

12. QR CODE LIFECYCLE

QR status:

ACTIVE

before event check-in.

When scanned successfully:

ACTIVE → USED

The ticket becomes invalid immediately.

A second scan must return:

ALREADY_USED

and must NOT allow entry.

13. QR CHECK-IN — PREVENT DOUBLE ENTRY

This is a critical concurrency requirement.

Two staff members could potentially scan the same QR at almost exactly the same time.

The backend must prevent both scans from succeeding.

Do NOT implement:

check ticket
if active:
    mark used

as two independent operations.

Use a transaction/atomic database operation/row lock or equivalent concurrency-safe mechanism.

Conceptually:

BEGIN TRANSACTION

Find ticket using secure QR token
Lock ticket record

IF ticket is already USED:
    reject

IF ticket is not valid:
    reject

Mark ticket as USED
Store check-in timestamp/staff information

COMMIT

Only one simultaneous scan may successfully consume the ticket.

14. CHECK-IN RESULT

A successful scan should return useful information to authorized staff:

VALID TICKET
Ticket ID
Ticket Type
Attendee Name
Check-in Time

Do not expose unnecessary personal information.

If already used:

TICKET ALREADY USED
First check-in time

If invalid:

INVALID TICKET

Do not reveal sensitive backend information.

15. CHECK-IN AUDIT LOG

Every scan attempt should be recorded where appropriate.

Track:

Ticket ID
Result
Timestamp
Staff/user who performed the scan
Relevant reason/status

Examples:

VALID
ALREADY_USED
INVALID

This allows administrators to investigate suspicious activity.

16. EMAIL DELIVERY

After approval and successful QR generation, automatically send the ticket to the applicant's registered email address.

The email should contain:

Event name
Attendee name
Ticket type
Ticket information
QR code
Important event instructions
Check-in instructions

Do not send the QR email before approval.

17. EMAIL FAILURE HANDLING

Do NOT mark the ticket as failed merely because an email provider temporarily fails.

Separate:

TICKET APPROVAL

from:

EMAIL DELIVERY

The ticket must remain valid even if email delivery temporarily fails.

Store email delivery state:

PENDING
SENT
FAILED

If sending fails:

Record the error internally.
Keep the approved ticket.
Allow controlled retry.
Prevent duplicate ticket generation.
Do not create a second QR unnecessarily.

Admin should be able to see that email delivery failed.

18. EMAIL RETRY / IDEMPOTENCY

Email sending must be safe to retry.

If the system retries an email:

Reuse the existing ticket.
Reuse the existing valid QR.
Do NOT create another ticket.
Do NOT create another registration record.
Do NOT charge the user again.
19. ADMIN DASHBOARD

Admin should be able to monitor all important activities.

Dashboard should provide:

Ticket statistics

Do NOT calculate revenue from frontend-submitted prices.

20. REVENUE TRACKING

Every approved ticket should have its authoritative ticket price stored.

Example:

Ticket Type: UNIVERSITY
Price: 200

or:

Ticket Type: OUTSIDER
Price: 1000

Store the price at the time of ticket issuance so historical records remain accurate even if future pricing configuration changes.

Maintain:

Ticket count by type
Revenue by type
Total revenue
Payment/slip verification state if applicable

Avoid floating-point errors for currency.

For Sri Lankan Rupees, use integer amounts where possible:

200
1000

rather than floating-point monetary values.

24. DUPLICATE REQUEST PROTECTION

Users may accidentally:

Double-click Submit.
Refresh.
Retry a failed request.
Lose connection and submit again.

The backend must prevent duplicate ticket creation.

Use idempotency keys or another reliable idempotency mechanism for ticket submission/approval operations where appropriate.

A repeated request must not create multiple tickets.

25. DATABASE TRANSACTIONS

Use transactions for operations that modify multiple related records.

For example:

Approve application
+
Create ticket
+
Generate QR record
+
Create audit record

must not leave the database in a partially completed state.

If a transaction fails:

Roll back safely.
Return a controlled error.
Do not leave orphaned records.
26. ERROR HANDLING

Create centralized backend error handling.

Errors must be:

Predictable
Structured
User-friendly
Logged internally
Free of sensitive implementation details

  "code": "REGISTRATION_NUMBER_ALREADY_USED",
  "message": "This university registration number has already been used."
}

Do not return raw database errors to users.

29. CHECK-IN PERFORMANCE

The check-in endpoint should perform only the necessary operations.

Do not load:

Entire activity history
Unnecessary user records

Use indexed lookup by QR token.

Return a fast, deterministic response.

34. DATABASE CONSISTENCY RULES

The following must always be true:

Rule 1

One university registration number → maximum one valid ticket/application according to the defined business rule.

Rule 2

One ticket → exactly one QR credential.

Rule 3

One active QR → one ticket.

Rule 4

One successful QR check-in → ticket becomes invalid/used.

Rule 5

A used QR can never become active again through a normal API operation.

Rule 6

Approval can only be performed by an authorized reviewer/admin.

Rule 7

Ticket price comes from backend-controlled configuration.

Rule 8

Outsiders do not require university registration numbers.

Rule 9

Email failure must not create duplicate tickets.

Rule 10

Concurrent requests must not bypass uniqueness or QR single-use rules.

36. CONCURRENCY TESTING

Specifically test race conditions.

Simulate:

Expected:

Request A → SUCCESS
Request B → DUPLICATE REGISTRATION

Scan A → VALID
Scan B → VALID

39. MOST IMPORTANT IMPLEMENTATION PRINCIPLE

Do not optimize only for the normal successful path.

The backend must be designed around:

What happens if the user clicks twice?

What happens if two users submit the same registration number simultaneously?

What happens if two staff scan the same QR simultaneously?

What happens if email fails?

What happens if the server restarts?

What happens if the frontend sends a manipulated price?

What happens if an unauthorized user calls the approval API directly?

What happens if the same approval request is sent twice?

Every one of these situations must have a deterministic, safe outcome.

FINAL REQUIREMENT

The finished backend must be:

Reliable + Fast + Secure + Concurrent-safe + Idempotent + Maintainable + Scalable + Error-tolerant

Do not leave placeholder business logic in the critical ticket/approval/QR/check-in flow.

Do not use mock success responses for production operations.

Run the backend.
Run the frontend.
Test every API.
Test the complete ticket lifecycle.
Test duplicate registration.
Test concurrent QR scans.
Test email failure/retry behavior.
Test price manipulation attempts.
Test unauthorized API access.
Test database failure handling.

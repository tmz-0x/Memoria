1. FIX SMTP RESET FUNCTIONALITY
Current problem

The SMTP configuration can be configured successfully, but the RESET functionality does not properly reset the configuration after SMTP settings have been configured.

Fix the existing reset implementation.

Do NOT simply clear the frontend form.

A reset must actually reset the persisted SMTP configuration and the active runtime SMTP configuration.

2. SMTP RESET MUST HANDLE ALL CONFIGURATION LAYERS

Inspect where SMTP configuration currently exists.

It may involve:

Environment variables
Database configuration
Runtime memory/cache
SMTP transport/connection pool
Frontend state
Browser state

Identify all active sources.

The reset operation must correctly handle the architecture actually being used.

After:

ADMIN → SMTP Settings → RESET

the system must not continue using the old administrator-configured SMTP settings unintentionally.

3. DEFINE CORRECT SMTP RESET BEHAVIOR

When an administrator selects:

Reset SMTP Configuration

show a confirmation dialog.

Example:

"Reset SMTP configuration? Email sending will stop until valid SMTP settings are configured again."

After confirmation:

Remove/reset the administrator-configured SMTP values from persistent storage.
Clear the active runtime SMTP configuration.
Destroy/recreate the SMTP transport if required.
Clear relevant cached configuration.
Return the system to the intended unconfigured/default state.
Do not accidentally restore stale values from frontend state.
Update the SMTP status displayed in the admin panel.
Record the operation in the audit log.
4. ENVIRONMENT VARIABLE BEHAVIOR

Be careful with .env configuration.

If environment variables are used as fallback configuration, clearly distinguish:

Initial/default configuration

from:

Administrator-managed runtime configuration

Do not make the RESET button appear to work while the backend immediately reloads the same SMTP values from environment variables.

If .env values are intentionally configured as permanent deployment defaults, clearly show that the system is using deployment-level SMTP configuration and that administrator reset cannot permanently remove those values.

Do not modify .env files from the browser.

The final behavior must be predictable.

The displayed count is currently incorrect.

This MUST be investigated at the backend/database level.

Do not simply modify the number displayed on the frontend.

Determine why the count is wrong.

Possible causes to investigate:

Duplicate database records
Duplicate API requests
React effect executing multiple times
Pagination count being confused with total count

Client-side counting

Find the actual root cause.

7. DEFINE EXACTLY WHAT "LOG COUNT" MEANS

Do not use ambiguous counting.

For every displayed log statistic, define exactly what it represents.

For example:

Total Logs =
COUNT of all eligible log records in the database

Error Logs =
COUNT of log records where severity = ERROR

Critical Logs =
COUNT where severity = CRITICAL

Submission Logs =
COUNT of actual submission log records

Do not count rows from a JOIN if the JOIN causes one log to appear multiple times.

Use:

COUNT(DISTINCT log.id)

where appropriate.

Adapt this to the existing database technology.

8. DATABASE AS SINGLE SOURCE OF TRUTH

The Admin dashboard must NOT calculate critical log counts using frontend arrays.

Do NOT do:

logs.length

unless logs represents the complete authoritative dataset.

Do NOT load the first 20 logs and then claim:

"Total logs = 20"

if there are actually 500 logs.

Instead, obtain the total count from the backend/database.

For example:

{
"items": [...],
"pagination": {
"page": 1,
"limit": 20,
"total": 500
}
}

Use the backend's authoritative total.

9. TEST/DEVELOPMENT LOGS MUST NOT CORRUPT PRODUCTION STATISTICS

The existing logs used for website testing must be reviewed.

Determine whether they are:

Real audit events
Development/test records
Sample/demo records
Temporary debugging logs

Do NOT blindly delete real historical logs.

Do NOT blindly include development sample data in production statistics.

If test records exist in the production database:

Identify them.
Determine how they were generated.
Remove them only if they are confirmed to be test/sample records.
Prevent test data from being generated in production again.

Production statistics must represent real system activity.

10. PREVENT DUPLICATE LOG CREATION

Inspect the application for situations where one action creates multiple identical logs.

For example:

One login
→ one login event

One ticket approval
→ one approval event

One QR check-in
→ one check-in event

Do not allow a single operation to create multiple identical audit records because multiple frontend effects, retries, or backend handlers execute the same logging operation.

Where appropriate, use:

Request IDs
Idempotency
Unique event identifiers
Transaction boundaries

Do not artificially hide duplicate logs in the UI.

Fix their creation.

11. LOG COUNTS MUST UPDATE CORRECTLY

Creating a log
